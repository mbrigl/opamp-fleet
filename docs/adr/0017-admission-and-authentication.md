# ADR-0017: Admission stacks a fleet credential and a Server-issued client certificate, proves membership rather than identity, and the Operator plane has Basic authentication of its own

- **Status:** ⚪ superseded by [ADR-0039](0039-admission-requires-both-proofs-and-enrolment-is-approved.md)
- **Date:** 2026-08-16
- **Deciders:** Markus Brigl
- **Applies to:** Admission on `/v1/opamp` in `crates/fleet-server/src/transport.rs`, `credentials.rs`, `tls.rs` and `ca.rs`, the Operator plane's guard in `crates/fleet-server/src/api.rs`, the Client's credential, identity and enrolment in `crates/fleet-agent/src/config.rs`, `tls.rs` and `csr.rs`, and the `[auth]`, `[tls]`, `[client_ca]` and `[rest.auth]` sections of `server.toml` and `supervisor.toml`

## Context

Goal 17 of the [specification](../SPECIFICATION.md) asks for TLS on both ends, mutual TLS, and a
Server that accepts only authenticated Agent identities. TLS
([ADR-0012](0012-transports-tls-and-the-servers-two-planes.md)) protects the channel and
authenticates nobody. The Baseline treats authentication as transport-level HTTP: methods MAY be
used, `401` MUST be returned on failure, and its own example of the credential is
`Authorization: Basic …` in `ConnectionSettings.headers`. On certificates the upstream text is
explicit about the layering: Agents *"will use some sort of header-based authorization mechanism
… and **optionally also** client-side certificates."* Its CSR flow — a regular TLS connection, a
keypair and CSR generated by the Agent, a certificate issued by the Server as a local CA or by a
CA it proxies to, `BadRequest` when issuance fails — keeps the private key on the host, and it
answers the bootstrap chicken-and-egg with *"a bootstrap client certificate that is already trusted
by the Server"*, whose distribution it leaves out of scope.

Forces that shape the answer:

- **Ecosystem practice is static headers, both schemes.** `opamp-go` clients send static headers;
  the Collector's `opampextension` sets `headers` or delegates to `basicauthextension` or
  `bearertokenauthextension`.
- **Zero-config must survive.** A lab without credentials keeps working
  ([ADR-0011](0011-workspace-crates-and-configuration.md)).
- **Authorization and tenancy are non-goals** of the specification: *that* a peer belongs to the
  fleet is in scope, *which* Agent may do *what* is not.
- **`instance_uid` is self-asserted.** An Agent chooses it, and the Server may re-key it at any time
  with `AgentIdentification`. A certificate whose validity depended on matching it would die on a
  re-key the Server itself initiated.
- **A Gateway terminates.** A Client in Gateway Mode reads OpAMP to fold many Agents onto few
  connections ([ADR-0009](0009-client-modes-and-the-gateway.md)), so the certificate the Server
  sees belongs to the Gateway; a header survives the hop, a peer certificate cannot.
- **The Agent plane serves one route that must stay open:** the package download, fetched with
  neither credential nor certificate ([ADR-0012](0012-transports-tls-and-the-servers-two-planes.md)
  clause 8).
- **The Operator plane's UI is one embedded page with no frontend toolchain.** Whatever guards the
  API must guard that page without a login form, a session store or a cookie. Tools whose UI is an
  operational page (Prometheus, Alertmanager, Traefik's dashboard) use HTTP Basic behind TLS; tools
  whose UI is the product (Grafana, BindPlane) ship sessions.

## Decision

We will admit a peer to `/v1/opamp` only when every configured proof succeeds — a static Basic or
Bearer credential, a client certificate issued through the Baseline's CSR flow, or both — treat
what admission proves as fleet membership with no authorization between admitted Agents, and guard
the Operator plane with a separate, optional set of Basic credentials.

1. **The Agent plane's credential is `[auth]`, optional and absent by default.** `server.toml`'s
   `[auth]` holds `bearer_tokens = ["…"]` and/or an `[auth.basic_users]` table of
   `user = "password"`; a section with no credential fails at startup. While present, every request
   to `/v1/opamp` — each plain-HTTP `POST` and the WebSocket upgrade `GET`, checked before the
   upgrade completes — must carry an `Authorization` header matching a configured credential, or is
   answered `401` with a `WWW-Authenticate` challenge naming exactly the configured schemes
   (`Basic realm="opamp"`, `Bearer`). Several accepted credentials are what make overlapping
   rotation possible. Absent, the endpoint is open.

2. **One credential primitive for both planes.** Accepted `Authorization` values are precomputed in
   full, and a presented header is compared against each in constant time with `constant_time_eq`
   ([`credentials.rs`](../../crates/fleet-server/src/credentials.rs)). The planes differ in what they pair
   the check with, never in how it compares.

3. **The Client sends exactly one credential.** `supervisor.toml`'s `[auth]` holds either
   `bearer_token` or `username`/`password`; both at once fail at startup. The resulting
   `Authorization` header rides every plain-HTTP request and the WebSocket upgrade. A `401` is
   logged as a credential failure and retried with the transport's backoff, so fixing credentials
   on either side needs no restart choreography. A Server-rotated credential outranks `[auth]`
   ([ADR-0018](0018-connection-settings-and-server-capabilities.md)). The Client warns when it is
   about to send a credential over `ws://` or `http://` to a host that is not loopback — the
   operator's choice, never an error.

4. **A credential-bearing offer without `[auth]` is warned about at startup.** A
   `[connection_offer]` carrying a credential or a `[telemetry_offer]` carrying headers, while
   `[auth]` is unset, hands that secret to anyone who connects; the Server logs a warning naming
   the sections rather than refusing, so the open default keeps working.

5. **Client certificates on both transports, verified at the TLS layer, required on the route.**
   `[tls] client_ca_file` in `server.toml` builds a rustls `WebPkiClientVerifier` with
   `allow_unauthenticated`: a presented certificate is always verified and a bad one is refused in
   the handshake, while a peer presenting none still completes it, because the Agent plane also
   serves the package download. `PeerCertAcceptor` wraps the rustls acceptor and carries the
   handshake's certificate, or its absence, into the request; `/v1/opamp` is the only route that
   reads it and answers `401` without one. The Client presents its identity on `wss://` (its rustls
   `ClientConfig`) and on `https://` (a reqwest `Identity::from_pem`).

6. **Every configured proof must succeed.** With `[auth]` alone the endpoint requires the
   credential; with `client_ca_file` alone it is certificate-only; with both, a request needs a
   valid credential **and** a connection bearing a valid certificate. There is no separate
   "required" switch: configuring a mechanism is what requires it, so adding mutual TLS never widens
   admission. The credential may be dropped only in a fleet without Gateways: behind a terminating
   Gateway it is the only per-Agent proof that reaches the Server (clause 13).

7. **A certificate proves membership, not identity.** The Server does not require the subject to
   match `instance_uid`, `service.instance.name`, or anything else an Agent reports; the subject is
   descriptive (the Client requests its `service.instance.name`) and authorizes nothing. The
   request may not dictate the certificate's powers either: the Server signs a client-authentication
   leaf only — `CA:FALSE`, `digitalSignature`, `clientAuth` — and drops any requested SANs.

8. **A Client has two sources for its identity, and the issued one wins.** An operator may provision
   one in `supervisor.toml`'s `[tls]` (`cert_file` and `key_file`, both or neither, beside
   `ca_file`); a Server-issued pair is stored in `state_dir` as `client-cert.pem` and
   `client-key.pem`. The stored pair outranks the file, the same precedence persisted connection
   settings have; deleting it reverts to what the operator wrote. The private key is written `0600`
   on Unix and inherits the state directory's ACL on Windows
   ([ADR-0014](0014-the-client-as-an-installed-service.md)).

9. **The Server signs CSRs as a local CA while `[client_ca]` is configured.** `[client_ca]` names
   `cert_file`, `key_file` and `validity_days` (default 90, `0` refused); it is its own key, never
   the listener's, because the CA key is the fleet's trust anchor. `AcceptsConnectionSettingsRequest`
   is declared only while the section is present, and a `[client_ca]` without `[tls]` fails at
   startup — it would issue certificates no listener asks for. A Client that has no certificate, or
   holds one in its renewal window, generates a keypair and a PEM CSR locally and sends it as
   `ConnectionSettingsRequest.opamp.certificate_request`, only once the Server has declared the
   capability ([ADR-0018](0018-connection-settings-and-server-capabilities.md) clause 15). A CSR
   that does not parse, or that arrives while no `[client_ca]` is configured, is answered with a
   `ServerErrorResponse` of type `BadRequest`. The issued certificate travels back as an ordinary
   connection-settings offer with no private key in it.

10. **A bootstrap certificate carries a host to its first CSR, and admission is the approval.** It
    is an ordinary client certificate, verified by the same `client_ca_file` and not told apart
    from an issued one, and it may be one certificate for the whole fleet — defensible only because
    of clause 6, under which it opens nothing without the credential beside it. A short validity
    limits its reach; distributing it is the operator's. A CSR from a peer that passed admission is
    signed; there is no manual approval queue.

11. **Renewal starts at two thirds of the validity, and the old certificate stays until the new one
    is proved.** The Client asks again once its certificate is two thirds through its life and
    keeps presenting the old one until the candidate has been verified by connecting with it
    ([ADR-0018](0018-connection-settings-and-server-capabilities.md) clause 5); on failure the
    previous certificate stays in force and the offer is reported `FAILED`.

12. **Issuance adds `rcgen`, `time` and `x509-parser`, and no system dependency.** `rcgen` (features
    stated: `crypto`, `ring`, `pem`, `x509-parser`) generates the CSR and signs it; `time` expresses
    validity; `x509-parser` reads a certificate's validity for the renewal window. The `ring` backend
    is the provider [ADR-0012](0012-transports-tls-and-the-servers-two-planes.md) already installs,
    so no OpenSSL and no cmake enter the build. `ring` compiles C and assembly in its build script,
    so a C compiler is needed either way; what this keeps is the absence of system libraries.

13. **Mutual TLS is per hop; the credential travels end to end.** Between an Agent and the Server
    through a Gateway there are two mutual-TLS connections, each proving the peer at that hop. The
    Gateway holds its own client identity for the upstream leg, obtained through the same CSR flow,
    and forwards the Agent's `Authorization` unchanged
    ([ADR-0009](0009-client-modes-and-the-gateway.md), which also owns the Gateway's downstream TLS
    keys).

14. **Admission is a fleet-wide trust boundary, and within it there is no authorization between
    Agents.** A report's `instance_uid` is self-asserted; any admitted peer may report under any
    `instance_uid`, and the Server takes it at face value. Per-Agent authorization is not added: the
    only mechanism that could provide it — binding a certificate to `instance_uid` — breaks
    Server-initiated re-keying, certificate renewal and Gateway Mode. Operators who need isolation
    between mutually distrusting Agents put them behind separate Servers or network segments. This
    is stated in [`SECURITY.md`](../../SECURITY.md) and in the Server's admission and identity
    module docs.

15. **The Operator plane is guarded as a whole by `[rest.auth]`, Basic only, optional.**
    `[rest.auth] basic_users` is a map of `user = "password"`; several users allow rotation and the
    withdrawal of one operator's credential. A section with no user, or an entry with an empty name
    or password, fails at startup. While present, every route on that listener — `/api/v1/…`,
    `/api/v1/openapi.json`, `/api/v1/docs` and the UI at `/` — answers `401` with
    `WWW-Authenticate: Basic realm="opamp"` without a matching credential; the browser prompts
    natively and re-sends the header, so the UI needs no login page, session or cookie. Absent, the
    plane is open, and its loopback default is what protects it
    ([ADR-0012](0012-transports-tls-and-the-servers-two-planes.md) clause 7). Authentication and
    reachability are independent settings. The Agent plane, the package download included, is
    untouched by it.

16. **A re-sent credential is not a cross-site licence.** The body-less `POST` acts on the Operator
    plane refuse a request whose `Sec-Fetch-Site` says it is cross-site (`403`), and every other
    mutating route is a JSON `PUT`/`DELETE` a browser sends only after a preflight this Server
    answers for nobody.

17. **A cleartext operator password is warned about, not refused.** With `[rest.auth]`, no `[tls]`
    and a `[rest] listen` that is not loopback, the Server logs a warning at startup. Refusing would
    break the legitimate case of a TLS-terminating proxy in front.

18. **The two credential sets stay separate, and neither carries roles.** The fleet's `[auth]`
    credential lives on every host and is rotated through offers; it is never the operator's
    password. Every authenticated operator can do everything the plane offers. Passwords and tokens
    are stored verbatim in `server.toml` in both sections, which change format together or not at
    all.

**Out of scope:** per-Agent credentials or identity; an opt-in strict mode binding certificate
subject to `instance_uid` where Gateway Mode and re-keying are off; proxying a CSR to an external
CA (it would sit behind `[client_ca]`); a separate bootstrap CA whose certificates may only enrol;
certificate revocation, for which short validity plus renewal stands in; where a fresh install gets
its bootstrap certificate; requiring the certificate in the TLS handshake; Bearer tokens on the
Operator plane (an additive key); hashed or referenced credential storage; an audit record of
operator actions.

## Alternatives considered

- **Mutual TLS as the only authentication** — demands a client PKI on day one, does nothing for the
  low-friction start, and forecloses Gateway Mode, where the credential is the only per-Agent proof
  that survives the hop. Clause 6 still makes a certificate-only fleet reachable by configuration.
- **Admission where any one configured proof suffices** — reads as the friendlier migration, but
  while `[auth]` is configured a leaked token walks past the mutual TLS that was just installed, and
  it inverts the specification's layering.
- **The credential as the bootstrap instead of a bootstrap certificate** — the "any one proof" rule
  narrowed to one message type, needing a per-message exception in admission that exists for no
  other purpose; the specification answers the question with a certificate.
- **Operator-provisioned certificates only, no CSR flow** — leaves every host's certificate to be
  created, delivered and renewed by hand, the errand the specification exists to remove. It
  survives as clause 8's first source.
- **The Server hands out certificate and private key** — every Agent's key would exist on the
  Server, travel the wire and sit in its storage; one compromised Server would yield the fleet's
  identities.
- **Binding the certificate subject to `instance_uid`, or trust-on-first-use pinning of the two** —
  a re-key, a renewal or an Agent moving between Gateways would read as impersonation, and one
  Gateway certificate legitimately carries many UIDs.
- **Rejecting a report whose `sequence_num` regresses** — an Agent restart legitimately resets it,
  and a forger can imitate a restart; it authorizes nothing.
- **Per-Agent credentials from a store** — identity management that brushes against the deferred
  authorization and tenancy non-goal.
- **Requiring client certificates at the listener** — refuses every peer fetching the package
  download, which presents none.
- **A manual approval queue for CSRs** — an operator workflow with UI and REST resource for a
  Server whose UI is rudimentary by design; an unattended queue is an outage that looks like a
  policy. A fleet that wants human approval withholds `[client_ca]`.
- **Hashing the stored passwords** — the right end state, but one section hashed and the other not would
  leave two formats in one file, and a KDF per request is its own denial-of-service question.
- **Pluggable authenticators (OIDC, JWT, external IdP)** — static credentials answer "belongs to
  the fleet"; a validator can be added behind the same seam later.
- **A login page with a session cookie on the Operator plane** — a session store, logout, cookie
  policy and CSRF protection inside a Server whose UI is an operational page; Basic gives the same
  browser experience for none of it.
- **Bearer only on the Operator plane** — a browser cannot send one without JavaScript holding a
  token, which drags the UI into session management.
- **Reusing `[auth]` for the Operator plane** — makes the fleet credential, present on every host,
  the operator's password.
- **Leaving operator authentication to a reverse proxy** — a property depending on an artifact this
  project neither ships nor tests.

## Consequences

- Positive: goal 17 holds — encrypted channel, proved peer, a proof this project issues and renews
  rather than one an operator distributes by hand; every mainstream OpAMP client can present the
  required header.
- Positive: adding mutual TLS to a running fleet can only tighten it; a half-finished rollout fails
  loudly as hosts that cannot connect, never silently as hosts admitted without the new proof.
- Positive: the trust model is explicit — one fleet is one trust domain — and the Operator plane
  can be published to a network without publishing the fleet's control surface.
- Negative / trade-offs: the Server is a CA, and its signing key can mint fleet members.
- Negative / trade-offs: an expired certificate locks a host out, credential or not. A Client
  switched off longer than its validity comes back unable to connect; recovery is the operator's —
  unset `client_ca_file`, let the host re-enrol, set it back — and is written in the manual.
- Negative / trade-offs: a bootstrap certificate still has to be distributed, mitigated by it being
  one for the fleet and opening nothing on its own.
- Negative / trade-offs: behind a Gateway the Server proves which Gateway a message came through,
  never which Agent produced it; the credential stays load-bearing in gatewayed fleets.
- Negative / trade-offs: a compromised admitted peer can poison another Agent's record, most easily
  over plain HTTP, which cannot tell pollers apart. Accepted within one fleet; it is not a
  cross-fleet or unauthenticated exposure.
- Negative / trade-offs: credentials sit verbatim in operator-owned files; Basic and Bearer over a
  non-TLS transport are cleartext, mitigated only by warnings; browsers cache Basic credentials and
  offer no clean logout.
- Follow-ups: hashed or referenced credential storage for `[auth]` and `[rest.auth]` together; an
  audit record of operator actions; a strict per-Agent identity mode; an external-CA backend; a
  revocation story if a fleet must eject a host faster than a certificate expires; the bootstrap
  certificate on a fresh install.
